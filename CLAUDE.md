# mfe-pot-employment-insurance-mfe

## What this is

The **EI application, claim status, and EI reporting** frontend for the mfe-pot Government of Canada MFE proof-of-technology. Federated as a remote into `mfe-pot-msca-shell`; also exposes a standalone EI-reporting-status widget embedded directly into `mfe-pot-dashboard-mfe`'s overview. The second app extracted from the platform repo, following job-bank's proven recipe.

## What's in this repo

- `apps/employment-insurance-mfe` — the frontend, federated on port `4204` in local dev. Repo directory, Nx project, federation identity (`federation.config.mjs`'s `name`), Docker image, and Helm chart/release are all named `employment-insurance-mfe` — the `-mfe` suffix disambiguates this internal federated remote from either host app's own front-door name (see the meta repo's `../CLAUDE.md`). The underlying business-domain naming (Nx `scope:employment-insurance` tag, `libs/data-access`, CMS content keys) deliberately stays un-suffixed — that's domain identity, not hosting identity. `apps/employment-insurance-mfe/src/app/*.tsx` holds every component directly (`App.tsx`, `Applications.tsx`, `Claims.tsx`, `Reporting.tsx`, `ReportingStatus.tsx`) — no separate `libs/<name>/feature-*` library the way this repo had before converting to React (see the platform repo's CLAUDE.md, "Components live in the app").
- `apps/employment-insurance-bff` — this app's dedicated BFF (port `3002`), plain Express/TypeScript, routes carry the `/api` prefix internally (`/api/applications`, `/api/claims`, `/api/reports`, `/health` at root). **Not** suffixed `-mfe` — no naming collision to disambiguate, no reason to touch it.
- `libs/data-access` — `EmploymentInsuranceApiClient`. The one library that stayed separate when this repo's feature libs folded into `apps/employment-insurance-mfe/src/app/`.
- `charts/employment-insurance-mfe` — deploys the frontend+BFF pair as one Helm release, following job-bank's chart shape exactly (this app had no Dockerfile or chart yet in the platform repo before extraction — both were authored fresh here).

Depends on published packages from GitHub Packages: `@tn4consulting/shared-auth`, `shared-auth-server`, `shared-content-client`, `shared-federation-config`, `shared-federation-runtime`, `shared-i18n`, `shared-locale-sync`, `shared-runtime-config`, `shared-session-cache`, `shared-ui-scds-core` (pinned in `package.json`; keep in sync with `platform-versions.json` in `mfe-pot-platform`). GCDS has been removed from the family entirely (see the platform repo's CLAUDE.md) — no wrapper package for SCDS either, `shared-ui-scds-core`'s custom elements (`scds-card`) are consumed directly via JSX, same as every other app.

## Repo-specific things worth knowing

- **`App` (`apps/employment-insurance-mfe/src/app/App.tsx`) renders a CMS-driven intro block** (`employment-insurance.intro` key, fetched via `ContentClient` — `content-client.ts`, same pattern as every other app's own `content-client.ts`) above the `Applications`/`Claims`/`Reporting` sections, re-fetched via a `useEffect` on cross-remote locale change. `runtime-config.ts`'s `strapiBaseUrl` points at `mfe-pot-platform`'s `charts/strapi` in a real deployment (`http://cms.mfe-pot.local`, browser-to-server, not in-cluster Service DNS). **The section headings/table-adjacent labels/buttons/status text are now CMS-driven too** (`employment-insurance.claims.*`/`.applications.*`/`.reporting.*`/`.reporting-status.*` keys, batch-fetched via `ContentClient.getPageContents` and the local `use-page-contents.ts` hook) — `App.tsx` threads `contentClient`/`locale` down to `Applications`/`Claims`/`Reporting` as props, same as `apiClient`; `ReportingStatus.tsx` self-constructs its own `contentClient` instead (see below). Templated strings (e.g. `Claim {id}`, `Status: {status}.`) use `@tn4consulting/shared-content-client`'s `fillTemplate`, a `{key}`-style helper distinct from `shared-i18n`'s Transloco-era `{{key}}` syntax — deliberately, since CMS content and app-chrome i18n are different systems. No component keeps its own hardcoded fallback text anymore — `createContentClient(strapiBaseUrl, assetBaseUrl)` (`content-client.ts`) always wraps Strapi with a `FallbackContentClient` backed by `public/assets/content-fallback/{en,fr}.json`, so a CMS outage degrades to bilingual fallback content instead of English-only text; see the platform repo's CLAUDE.md "i18n" section for the full mechanism.
- **`ReportingStatus.tsx` is rendered directly by this app's own `App.tsx`**, after `Reporting`, and also embedded by `mfe-pot-dashboard-mfe`'s Overview page again (via `./EiReportingStatusWidget`, loaded through the generic `useWidgetLoader('ei-reporting-status')`, host-mediated through `mfe-pot-msca-shell` — see the platform repo's CLAUDE.md "Design principles" section). That embed was dropped for a while (`docs/msca-screenshots/dashboard.png` has no EI-reporting-status tile on the dashboard page) and is back now behind a feature flag, default off, so both render paths matter again — not just this app's own page. `ReportingStatus.tsx` is fully self-configuring either way (fetches its own runtime config, API client, content client); its one addition for cross-remote embedding is an optional `parentTraceparent` prop (`@tn4consulting/shared-observability`'s `withRemoteParent`, for joining the composing page's trace — see the platform repo's CLAUDE.md "Observability" section), additive alongside the existing optional `onStatusLoaded` callback prop. It used to be the one real consumer in the family of `shared-i18n`'s `{{param}}` interpolation; migrated to CMS content + `fillTemplate` for `reportingStatus.nextReportDue` (still takes a pre-formatted `Intl.DateTimeFormat` date string plus a raw day count) — the `reportingStatus.*` block was removed from `public/assets/i18n/{en,fr}.json` once migrated.
- **`federation.config.mjs`'s `exposes` map (`./Component`, `./EiReportingStatusWidget`) must point at `apps/employment-insurance-mfe/...`, not the pre-rename `apps/employment-insurance/...`** — confirmed this is exactly the gotcha the platform repo's CLAUDE.md documents ("`federation.config.mjs`'s `exposes` map needs checking on any app that exposes something beyond its own root component") — a stale path here fails the federation build with `FsPath ... does not exist`.
- **`scds-card`'s optional, `reflect: false` props (`description`, `tone`) render correctly via a plain JSX attribute, even though they never show up in `outerHTML`/`getAttribute()`** — confirmed by inspecting the live shadow DOM directly, not just the DOM attributes, while debugging what first looked like a real rendering bug in `Applications.tsx`'s confirmation card. See the platform repo's CLAUDE.md "GC Design System" section for the general rule.
- **`tsconfig.base.json` explicitly sets `"types": ["node"]`** — a defensive fix for a gotcha found during this app's own extraction: TypeScript's implicit `@types` auto-inclusion silently failed to pick up `@types/node` when `ts-node` compiled `jest.config.cts` through the plain `tsconfig.json` (root cause never fully isolated — likely an interaction between TS's auto-inclusion and pnpm's symlinked `node_modules/@types` layout under `moduleResolution: "bundler"`). Don't remove this line without confirming the underlying TS/pnpm interaction is actually fixed upstream.
- **`.tool-versions` and `pnpm-workspace.yaml` matter more than they look**: this repo's own extraction briefly lost both in a copy-paste from job-bank's file list, which silently fell back to the global default Node (22.7.0) and reproduced the exact `"require() of ES Module ... not supported"` error the platform CLAUDE.md documents as a Node<22.12 symptom — a real error pointing at the wrong root cause. If a build here ever throws that error, check these two files exist and are correct before chasing an ESM/native-federation theory.
- **`dashboardBffBaseUrl`-style same-origin pattern**: `runtime-config.ts`'s `employmentInsuranceBffBaseUrl` dev default is `http://localhost:3002`; the chart overrides it to `/api` — same-origin Ingress path rule, not a second hostname.
- **CI** (`.github/workflows/ci.yml`): lint/test/build (including `employment-insurance-bff`'s separately-run `eslint:lint` target), then builds both images, spins up an ephemeral `kind` cluster, `helm install`s this chart, and curls the Ingress-routed hostname to confirm it serves. See `README.md` for local install/serve/build/Docker/Helm instructions.
